03

迁移流程

四个阶段，核心是阶段 2 的单单元循环；门禁从便宜到贵，任一层失败立刻停。

0PHASE

冻结基线

skylint migration baseline <repo>。必须在任何改动之前、用同一版本采集。后面所有门禁都以它为判据。

1PHASE

切单元图

skylint migration plan <repo>。产出单元清单与拓扑批次。

2PHASE

单单元循环

取活、生成作业单、agent 改代码、逐层过门禁、人工确认。失败不是异常，回滚后带着原因重试。

3PHASE

收口

全量重跑（所有页面，不只是改过的）、清理带失效条件的 workaround、出迁移报告。

六层门禁，从便宜到贵，任一层失败立刻停。L0 → L5

六层门禁的内容、确定性与相对成本
层 内容 确定性 成本 · 低 → 高
L0 skylint verify 字段级 diff，新增诊断必须为 0 确定
L1 生产构建（minidev build --no-pack） 确定
L2 automator 冒烟（会 flaky，重跑 3 次取多数） 半确定
L3 截图对比 + 阈值 半确定
L4 AI 判定，只吃 L0–L3 的证据，不自己重看代码 不确定，只判一次并固化
L5 人工确认（挂起等人，可等几天，不占算力） 人
一条硬规则
AI 判定拒收时返回数据，而不是抛异常。

抛异常会触发重试，重试会换一次结论，同一个组件可能一次过一次不过，无法解释「当初为什么接受」。所以拒收要作为数据返回，只判一次并固化。

12 条真机问题的三档分工

用短剧插件实际踩到的问题给自动化定标：哪些直接改，哪些必须人看，哪些工具不该碰。

A B C
A · 5 条 可直接机械改 B · 5 条 出 patch 但必须人看 C · 2 类 工具不该碰
12 条真机问题按自动化程度分为 A、B、C 三档
档 条数 特征 例子
A可直接机械改 5 语义可证明等价
  • scroll-view / swiper 的 padding 挪到内层
  • fit-content → auto
  • 删掉透明图标上的 box-shadow
  • line-height 1.4 → 1.5
  • 补 flex-shrink: 0
B出 patch 但必须人看 5 需要判断意图或跨文件影响
  • z-index 重排
  • dragHide 门控
  • WXS 同步测量改回调
  • createVideoContext → selectorQuery.context()
  • scroll-view 高度回写
C工具不该碰 2 类 引擎 bug / 需要真机
  • 渲染引擎的 absolute 高度计算
  • 1px 裁切
  • 小窗能力缺口

能自动化的比例比直觉少，但那一小块价值很高。

所以形态不是「一键迁移器」，而是「迁移流水线 + 人机分工」。

05

编排层

可选实现，不是必须。没有它，四条命令也能构成一条完整流水线。

编排器用 Vercel Workflow SDK，不是自研 runner。

本地零服务 挂起不占算力 重试语义分三档
编排器

循环、重试、挂起；不碰规则、不碰样式语义。

Agent

只读 job.json，只改当前单元。

skylint

确定性命令；只认退出码与 --json。

人

接受或打回；挂起可等几天，不占算力。

只依赖上面那几条命令，不认识任何具体 coding agent（codex / claude / opencode 只换一个命令行）。

已实测 · 端到端
agent 故意引入错误 → L0 拦住 → 回滚 → 重试改对 → 判定 → 挂起等人 → kill 进程重启后仍能继续

agent 与判定不重跑。不确定的判定被固化成确定的数据。

没有编排器也能手动跑：四条命令就是一条完整流水线，可以直接进 CI。
